# ALZ format (.alz) — observed behavior and implementation status

This document describes ALZ observations from ALZip 8 reference archives and the
current C implementation. It is not a claim of complete ALZ compatibility.
Exact parity is the project requirement; features without fixtures or explicit
verification remain open in [PLANS.md](../_work/PLANS.md).

## Evidence and verification scope

The checked-in corpus contains **62 `.alz` archives** generated by ALZip 8.0
plus continuation volumes, and `packed_egg/` holds the EGG samples (every EGG
profile, plus split and password variants and the solid variants of the two
profiles that accept `-s`; ALZ itself cannot be solid, see below).
`packed_alz_8.0/` adds the encrypted ALZ references used by `make test`:
`enc_basic.alz` (one member, ZipCrypto), `enc_basic_paths.alz` (eight members
with paths, one password verifier each), `enc_basic_split.alz` + `.a00`
(a ciphertext stream continued across two volumes) and
`unicode_basic_encrypted.alz` (non-ASCII names). They were produced by
`ALZipCon -a -tp0 -psecret`; the prototype `enc_basic.alz` also sits in
`corpus/` with a different random verifier. `packed_alz_8.0/` adds
the six ALZ references of the lot-H pass: `enc_alz_m0..m3.alz`, one per profile
(No Compression, Faster, Fast, Normal), `enc_alz_empty.alz` (an empty member
under `-psecret`) and `enc_alz_attrs.alz` (two members, one of them read-only),
plus the two non-ASCII-password samples `enc_alz_napw_euro.alz` and
`enc_alz_napw_euro_records.alz`. The ALZ set
covers **every compression profile ALZip 8 exposes for ALZ** — No Compression,
Faster, Fast and Normal — not a subset of them, as the ALZ plugin's own string
table confirms
(see below). `tools/header_dump.py` inspects container fields;
`tools/archive_compare.py` compares generated archives at the record/member/data
level, masking only the DOS timestamp when a test supplies that timestamp as an
input. The current test suite is corpus-specific: it does not exercise EGG, and
it cannot exercise ALZ container methods that no ALZ profile emits.

Dumping every member of the 62 archives yields only container method 0 (Store)
and container method 2 (Deflate); no member uses container method 1 (BZip2) or
container method 3, and no member of those 62 is encrypted. `make test` asserts
that matrix, so a newly added archive that breaks it fails the suite. The
encrypted references are a separate, explicitly listed set (above), never part
of the 62-archive profile matrix.

## Container overview

All multi-byte fields are little-endian. An archive/volume begins with an
8-byte ALZ header, followed by file records/data and a 16-byte END record.

### Archive header — 8 bytes per volume

| Offset | Size | Meaning |
|---:|---:|---|
| 0 | 4 | `41 4C 5A 01` (`ALZ\001`) |
| 4 | 2 | Unknown; observed `0A 00` in the corpus |
| 6 | 1 | Unknown; observed zero in the corpus |
| 7 | 1 | Volume index: 0 for `.alz`, 1 for `.a00`, 2 for `.a01`, … |

The specification groups bytes 4–6 as unknown. The split above is an observed
interpretation; unknown fields are not fully characterized.

### File header (`BLZ\001`)

| Offset | Size | Meaning |
|---:|---:|---|
| 0 | 4 | `42 4C 5A 01` (`BLZ\001`) |
| 4 | 2 | Filename byte length, UInt16 LE |
| 6 | 1 | Attribute bits (read-only, hidden, directory, file per the format reference); corpus entries observed as 0 |
| 7 | 4 | DOS timestamp |
| 11 | 1 | `fd` flags / optional-field size selector |
| 12 | 1 | Unknown2; observed as 0 in corpus |
| 13 onward | optional | Present when `fd & 0xF0 != 0`: method, unknown3, CRC32, csize, usize, then filename bytes |

The upper nibble of `fd` gives the byte length of each size field: `0x10` = 1,
`0x20` = 2, `0x40` = 4, `0x80` = 8 bytes. The corpus commonly uses 2- or
4-byte fields; the implementation chooses the field length from
`max(csize, usize)`. If the upper nibble is zero (observed for the empty-file
sample), method/CRC/sizes are absent. Filename bytes are historically code-page
data; ASCII is covered, while CP949 and other code-page behavior still require
exact tests.

`fd` bit 0 marks a ZipCrypto member (the ALZ plugin advertises only
`Zip 2.0 Compatible`). The member's stored data then starts with the **12-byte
password verify header**, followed by `csize` bytes of encrypted compressed
stream; `csize` **excludes** those 12 bytes (measured on `enc_basic.alz`: 64
stored ciphertext bytes for a 65-byte member, 12 + 64 bytes of data span). The
verifier is the usual PKZIP 12-byte header encrypted with the password-derived
key stream; once decrypted, its last two bytes are the **high half of the
member's CRC-32, low byte first** (`plain[10] = crc >> 16`, `plain[11] = crc >>
24`). ALZip fills the first ten bytes with a per-member random material that is
not derivable; seven references (three in EGG, four in ALZ) show the same
structure. Decryption is stream-continuous across volume boundaries. Other flag
interpretations must be validated against ALZip samples, not inferred only from
unalz behavior.

### END record — 16 bytes per volume

| Offset | Size | Meaning |
|---:|---:|---|
| 0 | 4 | `43 4C 5A 01` (`CLZ\001`) |
| 4 | 4 | Unknown; observed zero |
| 8 | 4 | Unknown / possible CRC; observed zero in this corpus |
| 12 | 4 | `CLZ\002` final volume; `CLZ\003` non-final volume |

These values are corpus observations, not a complete characterization of all
valid END records.

## Multi-volume observations

The observed span-volume target is 102,400 bytes. Each volume has its own 8-byte
archive header and 16-byte END record. For `records_span100k_fast`, the member
header is emitted once in the starting volume; compressed bytes continue at
offset 8 of the next volume. The observed compressed byte counts are 102,338
bytes in the first volume and 50,833 in the continuation, totaling csize 153,171.

This proves that case, not all possible boundaries. The corpus also holds three
16-volume chains over the 1.5 MiB `corpus/span/random1m.bin`
(`span_15vol_m0.alz`, `span_15vol_m2.alz`, `span_15vol_crypt.alz` + `.a00`…
`.a14`); `make test` reads each back from `.alz` and compares the payload, so
multiple continuation volumes, an encrypted chain and a final volume shorter
than 102,400 bytes are pinned. The C reader/writer's coverage must still include
one-byte remainders, a member beginning near a boundary, missing/reordered
volumes, and headers or member names close to the END region.

## Compression methods and sampled profiles

ALZ uses two unrelated numbering systems. Do not conflate them.

**Container method ID** — the one-byte `meth` field of a member's optional
fields (present when `fd & 0xF0 != 0`). The format reference and the historical
UnAlz enum (`COMPRESSION_METHOD` in `research/unalz/UnAlz.h`) agree:

| Container method ID | Meaning | Present in the 62-archive ALZ corpus? |
|---:|---|---|
| 0 | Store | Yes — every `_none` member except the mislabeled `image24_none` |
| 1 | BZip2 | **No** — and no ALZ writer can produce it, so the port refuses it |
| 2 | raw DEFLATE | Yes — every `_faster`, `_fast`, `_normal` member |
| 3 | DEFLATE with obfuscated initialization | **No** — unalz itself calls this `COMP_UNKNOWN`; refused by the port |

**GUI/CLI compression profile** — the user-visible choice, which is *not* a
container method ID. ALZip 8's console help
(`research/Program Files (x86)/ALZip/con_en-US.dll`, option `-m`) lists the
accepted numbers per format: `ALZ 1~3`, `EGG 1~4 (4 : Optimized Compression)`,
`ZIP 1~4`, with `0` documented as “No compression. Higher number leads to higher
compression ratio”. The ALZ plugin's own string table (`Formats/Alz.dll`,
ALZip 8.0.0.18) lists the profile labels `Nocomp`/`NoComp`/`None`/`Store`,
`Faster`, `Fast`, `Normal` next to the coder name `Deflate`, i.e. exactly four
ALZ profiles: No Compression plus three Deflate levels. The GUI lists them in the
order `Normal`, `Fast`, `Faster`, `No compression` (observed in the compression
dialog; the EGG dialog uses a different order and different wording, see
FORMAT-EGG §14.1 and FIXTURES lot I). All three compressed ALZ profiles write
container method 2. In this document **“method 1” always means the container
method ID 1 (BZip2)**; it is never the GUI/CLI profile `m1`.

**ALZip 12.30 update (the writer reference).** Measured on `code.c`,
`records.bin` and `biased.bin` with the local 12.30 `ALZipCon.exe` under Wine:
`-m1` = zlib level 1, `-m2` = zlib level 4 (the default), and `-m3` exits 0
**without writing any file**. 12.30 therefore keeps only three ALZ choices
(store + two deflate levels); the level-2 “Fast” profile of 8.0 has no 12.30
number. It also writes `attr=0x20` (`FILE_ATTRIBUTE_ARCHIVE`) on every regular
file, where the 8.0 corpus has `attr=0x00`. The port follows 12.30: `-p
none|faster|normal`, default `normal`, `-m3`/`-p fast` refused without output
(FIXTURES lot K, `make test` step 3).

Why no corpus archive carries container method 1 or 3: the ALZ set already covers
all four ALZ profiles, and ALZip 8's ALZ writer has no BZip2 coder at all.
`Formats/Alz.dll` contains no `bzip`/`BZ2` string — neither ASCII nor UTF-16 —
while BZip2 ships separately as `Coders/BZ2.dll` (“ALZip BZ2 Library”, bundled
libbzip2 1.0.5), the coder EGG uses for its own BZip2 method. Both methods are
therefore legacy/format-spec names without a producer: unalz itself labels method
3 `COMP_UNKNOWN`, and no reference sample can exist for either one. The port does
not implement them — `extract` refuses such a member with an explicit error and
`make test` asserts that refusal — rather than carrying a codec that nothing can
validate. BZip2 in this project belongs to EGG method 2, where the GUI does
select it and real samples exist. Whether a pre-ALZip-8 writer or an undocumented
switch ever emitted method 1 or 3 is unverified.

For the sampled ALZip 8 profiles, `tools/deflate_verify.py` previously matched
65/65 sampled method-2 members against raw zlib DEFLATE using the following
settings. This is the **8.0** scale; 12.30 writes level 1 for `-m1` and level 4
for `-m2`, and no longer offers level 2. The suffix column lists the corpus
filename aliases, not GUI names.

| Corpus suffix | ALZ GUI profile label | Container method ID | Observed deflate setting |
|---|---|---:|---|
| `none` | No Compression | 0 | Store in ordinary samples |
| `faster` | Faster | 2 | zlib level 1 |
| `fast` | Fast | 2 | zlib level 2 |
| `normal` | Normal | 2 | zlib level 4 |

Common observed parameters: `windowBits=-15` (raw DEFLATE), `memLevel=8`,
`Z_DEFAULT_STRATEGY`. The current C encoder uses vendored zlib 1.3.1; the ALZip
reference plugin was identified as zlib 1.2.3. Matching sample output is
verified, but the version difference and untested edge cases remain matters for
the exact-parity suite.

`image24_none.alz` is mislabeled relative to the profile suffix: its BLZ header
selects method 2 (raw DEFLATE), and its complete member stream is byte-identical
to `image24_fast.alz`. It is therefore not a Store/No Compression reference
sample. The suite retains this archive and regenerates it using the method
actually present (the `fast` profile); it must not be used to infer how ALZip
creates a true No Compression archive.

## Solid-Compression is not available for ALZ

Solid-Compression is an **EGG-only** feature. No ALZ archive can be solid, so
there is no ALZ solid mode to implement, no ALZ solid fixture to obtain, and no
solid/profile/span/password interaction to reproduce on this side. The ALZip 8.0
resources state it explicitly (`research/Program Files (x86)/ALZip/`):

- CLI (`con_en-US.dll`, option `-s`): "Compress with Solid-Compression method" …
  "ATTN: Solid-Compression doesn't support spanning archive or encryption. In
  addition, it can only be used in EGG file archive." A non-EGG format fails the
  format check with "ERROR : The format doesn't support Solid-Compression".
- GUI (`en-US.dll`): "Solid-Compression is available only in EGG archive." and
  "Only EGG format can use Solid Compression."

The port mirrors that refusal: `alzgg create -s …` prints `ERROR : The format
doesn't support Solid-Compression` and writes nothing (asserted by `make test`).
The other ALZ option surfaces are unaffected — spanning is available for ALZ
(see the multi-volume section) and encryption is the plugin's
`Zip 2.0 Compatible` method — so the solid-specific exclusions documented for
EGG (only two profiles, no spanning, no password) never apply to ALZ. See
[FORMAT-EGG.md](FORMAT-EGG.md) §14 for the EGG-side rules and their reference
wording.

## Current C implementation — not full parity

`src/cli_alz.c` (reached through the single `alz` binary, `src/alz.c`) currently
provides ALZ list/extract/create for the tested subset;
`src/alz_inflate.c` decodes the raw DEFLATE of container method 2, the only
compression method any ALZ profile writes. Container methods 1 and 3 are **not
implemented**: a member claiming them is refused with an explicit error, because
no ALZ profile emits them and no reference sample can exist, so a decoder for
them could never be validated. ZipCrypto is implemented in both directions:
`-p PASSWORD` on `extract`, and `--password PASS` on `create` (with
`--crypt-info HEX,…` to inject the per-member random material; without it
`/dev/urandom` supplies it, as ALZip does). The writer reproduces
`enc_basic.alz`, `enc_basic_paths.alz` (eight members, one verifier each) and
`enc_basic_split.alz` + `.a00` byte for byte, and also `enc_alz_m0..m3.alz`,
`enc_alz_empty.alz`, `enc_alz_attrs.alz` and the two `enc_alz_napw_*` samples
(eleven archive files in all, `unicode_basic_encrypted.alz` excepted, which is read-verified only). Two of those settle questions the lot-B set left open:

- **An empty member is stored with no optional fields at all** — `fd = 0`, no
  method, CRC, sizes or 12-byte verifier, so the archive looks exactly as if
  `-p` had not been given (`enc_alz_empty.alz`, 46 bytes). The writer reproduces
  that rather than refusing the input.
- **A non-ASCII password goes through the ANSI code page** of the system, as in
  EGG (FORMAT-EGG.md §12.9): `€` is fed to ZipCrypto as the single byte `0x80`,
  not as its UTF-8 or Latin-1 form, and a character absent from the page becomes
  `?`. `enc_alz_napw_euro.alz` and `enc_alz_napw_euro_records.alz` pin this for
  a 65-byte and a 240,000-byte member, and both are rebuilt byte for byte.

The `--attr` option takes one DOS attribute value or one per member; the
read-only member of `enc_alz_attrs.alz` shows that the attribute byte and the
encryption flag coexist independently (`fd = 0x21`, `attr = 0x01`).
The encoder exposes `none`, `faster`, `fast`, and `normal`, spans volumes with
`-v`, and refuses the EGG-only `-s` (Solid-Compression, above); it does not
implement all metadata, path encodings, or format options demonstrated by
ALZip. `-T` accepts one DOS timestamp for the whole archive or a comma-separated
list with one timestamp per member, which is what a multi-member reference needs
(ALZip stores each member's own mtime).
Multi-volume handling is tested against the included span fixtures, not all
boundary cases.

The test suite compares the implementation against the 62 checked-in sample
archives, asserts the profile→container-method coverage of that corpus, and
asserts that container methods 1 and 3 are refused. Its successful result means
only that those tests passed. It is not full ALZ format parity.
See [PLANS.md](../_work/PLANS.md) for the mode-by-mode coverage matrix and mandatory
remaining work.
